# Sakura Crossing 技术与扩展研究路线

下一步优先研究渲染复用和场景配置：把现有小街拆成可组合的房屋、道路、树木与交互入口，用同一套三渲二管线搭建不同布局，再测量扩大场景的成本。这条路线能回答它是否适合作为后续村庄、互动展示和小型探索场景的技术底座。

现有演示已经验证了一套独立街景与内容交互流程，并完成 [最小小镇搭建器](builder.md) 的三类物件编辑、本机保存和 JSON 导入导出。后续已完成 [三场景技术实验](lab.md)，支持共用组件、配置切换、风格调节和性能采样；外部模型适配与真实目标设备的规模基准仍待研究。前两阶段结果见 [实验记录](experiment.md) 与 [业务场景记录](business.md)。

## 第一优先级 渲染能否稳定复用

先建立固定镜头与光照的模型测试场，放入方块、曲面屋顶、树冠、带纹理招牌和透明窗，再接入一个授权明确的 GLB 模型。逐项比较分段光照、描线与调色的开关，记录哪些模型需要调整法线、材质或配色。三渲二观感同时依赖模型形状、纹理和构图；接入同一套材质并不保证所有资产都呈现相同效果。

把色阶、暗部色、轮廓宽度与调色参数收敛为风格预设，让不同场景共用预设。测试时固定视角保存对照图，并分别检查轮廓断裂、远处线条粗细、透明面的深度表现和颜色转换。

本地暗部染色通过 `onBeforeCompile` 替换 Three.js 着色器片段，依赖具体源码文本。应先锁定 r180，增加补丁匹配失败的可见诊断，再单独研究升级兼容性。[官方 Material 文档](https://threejs.org/docs/pages/Material.html)说明这个钩子用于 WebGLRenderer；转向 WebGPU 需要另行研究节点材质与后处理迁移，不能只替换渲染器。

色阶纹理与普通颜色纹理也要分别管理。[MeshToonMaterial 文档](https://threejs.org/docs/pages/MeshToonMaterial.html)要求色阶纹理使用最近邻过滤，并把它作为非颜色数据处理，避免额外颜色转换改变分段光照。

**完成条件：**同一预设能够应用到多种测试对象，差异和适配要求有对照图；渲染模块不依赖某一家店或某一条街的业务内容。

## 第二优先级 用配置组合村庄

将房屋、商店、树木、道路、路灯等生成函数拆成组件，组件接收尺寸、位置、朝向、配色和随机种子。最小搭建器已在共用组件上实现选择、拖动、增删、旋转与撤销，后续需要更丰富的参数和布局约束。场景配置描述组件如何排列，交互配置通过地点 ID 绑定动作。先使用简单配置文件，保留可复现的随机种子；最小搭建器的编辑存档采用独立的 sakura-town v1 格式；扩充协议时需定义迁移。

第一组实验使用相同组件和渲染预设，组合三种场景：沿路排布的樱花商业街、建筑分散的林间村落、围绕公共空间的小广场。重点比较布局变化后，道路衔接、建筑间距、镜头构图和交互入口是否仍然可用。

这里需要区分两种能力：配置搭建通过明确的位置和尺寸组合场景；自动生成村庄还要处理道路连接、建筑避让、地形适配和路线可达性。应先完成配置搭建，再用布局规则生成配置。随机摆放建筑只能验证数量增长，不能证明生成了可使用的村庄。

**完成条件：**切换三份配置即可得到三个不同布局，生成逻辑和渲染逻辑共用；入口不遮挡，建筑不重叠，道路能连接需要到达的地点。

## 第三优先级 建立规模与设备基准

先在相同设备、镜头、随机种子和渲染设置下测试，再决定优化方法。建议用 10、50、100 栋房屋作为初始实验梯度；这些是待测试的数量，不代表已支持的容量。记录首次可交互时间、帧间隔中位数与第 95 百分位、绘制调用、三角形数量，以及连续切换场景后的资源数量变化。帧间隔包含浏览器调度影响，不能直接当作 GPU 耗时。

[WebGLRenderer 文档](https://threejs.org/docs/pages/WebGLRenderer.html)中的 `renderer.info` 可提供绘制与资源统计；多次渲染组成一帧时，应汇总后统一重置。它的几何体和纹理计数不等于显存字节数，也不能替代帧率测试。

重复的窗户、路灯和树木可以研究实例化。[InstancedMesh 文档](https://threejs.org/docs/pages/InstancedMesh.html)说明，共用几何体和材质的多个对象可以减少绘制调用。独立开门、不同材质与交互拾取则需要分别设计，不能把所有建筑直接合为一个实例集合。

如果瓶颈随绘制调用增长，再研究实例化或合批；如果主要受像素数量影响，再调整分辨率、阴影和后处理质量；如果来自可见范围，再研究分区加载与远处简化模型。切换场景时还要明确共享材质、纹理和缓存的所有权，按需释放资源。

**完成条件：**得到可复现的测量记录，选定目标设备和可接受预算，再给出场景规模建议。目前没有真实触屏与低性能设备基准。

## 交互和外部资产的后续研究

交互先保持点击地点和镜头浏览，抽象成“地点 ID → 动作”的映射，再按用途增加步行、任务或叙事。可行走场景必须让可见地形、碰撞和高度查询保持一致，并验证路线可达；键盘操作和真实触屏操作也要分别验证。

外部资产从一个授权明确的小型模型开始。[GLTFLoader 文档](https://threejs.org/docs/pages/GLTFLoader.html)提供 glTF 2.0 场景与动画的加载能力；它不会自动统一模型风格。实验应比较原始材质与三渲二材质，检查纹理、透明度、法线、尺寸和动画适配，并记录来源与授权。

## 扩展方向与选择顺序

具体产品方向、用户流程、待补能力、最小方案与完成条件统一整理在 [能力理解与产品扩展](product-directions.md)，网页的理解与扩展页读取同一份 [结构化数据](product-directions.json)。下表保留技术推进顺序。

| 扩展方向 | 可以提供的能力 | 需要新增的关键部分 | 顺序建议 |
| --- | --- | --- | --- |
| 可配置场景组件集 | 用同一风格快速搭建街道、村庄和小广场 | 组件参数、配置校验、布局规则与性能预算 | 优先研究，能服务后续各方向 |
| 内容或品牌互动展示 | 让店铺、告示牌和亭子承载资料、作品或活动 | 内容数据映射、可访问入口；按业务需要接服务端 | 在现有流程上继续扩展 |
| 小型探索与叙事场景 | 在村庄中行走、发现地点和完成任务 | 移动、碰撞、任务状态、存档与叙事内容 | 规模基准明确后推进 |
| 场景编辑器或 AI 辅助搭建 | 最小搭建器已有编辑、撤销和 JSON 配置导入 | 扩充模板、避让与道路规则；再接受约束的 AI 草案 | 最小编辑已完成，按实际创作反馈推进 |

对本研究集，优先积累可复用的渲染方法、场景组件、配置示例和基准记录。这些成果能减少未来每个互动场景重复搭建的工作；制作效率提升多少，需要在后续项目中实际比较。

AI 辅助方向可以先生成受约束的场景配置，再经过校验和预览。允许的建筑类型、尺寸范围、道路与避让规则需要预先定义；任意描述自动得到完整可玩世界，超出了当前已验证能力。
