## 1. 能力是什么

它是由 Tampermonkey、Violentmonkey 等用户脚本管理器运行的 JavaScript 脚本。匹配范围是 Telegram 网页域名，主逻辑在单个 `src/tel_download.js` 中；使用当前已登录网页的媒体地址和客户端能力，无独立后台服务。

| 能力 | 实现证据 | 实测边界 |
| --- | --- | --- |
| 图片保存 | `tel_download_image`，L468–480；WebA L602–634，WebK L807–829 | 当前媒体地址可能是网页提供的显示版本；画质和原图来源待核对 |
| 视频保存 | `tel_download_video`，L150–321；官方下载按钮复用 L740–805 | 多分辨率、Blob 地址、网站变化和文件完整性待实测 |
| GIF 类动画 | 播放器按视频路径处理，WebA L548–563；WebK L786–805 | 保存格式跟随网页实际媒体，不承诺得到 `.gif` 文件 |
| 语音与圆形视频消息 | WebK `audio-element`、置顶音频控件，L640–683 | 需音频来源已加载；WebA 主线未提供同等语音入口 |
| Stories | WebA L486–531；WebK L685–726 | 当前故事页面选择器和媒体来源待实测 |
| 视频进度 | L55–148；自有视频下载函数调用更新 | 官方下载路径可能走浏览器下载管理；不能承诺每种路径都有自有进度 |

所查主线没有成熟的整频道归档、持久化下载队列、文字聊天导出、断点续传或知识库。批量下载存在 [Issue #159](https://github.com/Neet-Nestor/Telegram-Media-Downloader/issues/159) 及关联提案，不据此写成已合入的能力。

访问范围取决于账号本身能查看的内容。脚本复用客户端已有媒体访问能力，没有加入未获访问权限频道的实现。

## 2. 效果是什么

目标体验是：打开媒体后恢复或新增保存按钮，点击后使用官方下载逻辑，或读取媒体数据保存到本地。对本来允许保存的聊天，上游建议使用官方按钮。

保存的是客户端可取得的媒体字节。源码没有画质增强、去水印、修复编码、视频转码或图片超分流程；文件名和后缀也不是质量证据。图片使用随机 `.jpeg` 文件名，音频默认 `.ogg`，视频会尝试从地址元数据提取文件名，再按 MIME 调整扩展名，这些均不等于执行格式转换。

多分辨率视频已有 [Issue #130](https://github.com/Neet-Nestor/Telegram-Media-Downloader/issues/130) 反馈。该讨论包含用户修正后的描述和不同网页版本的差异，不能概括为所有视频都无法下载，也不能当作本研究复现结果。

本地网页使用原创 SVG 风景、合成语音波形和固定示例数据，展示按钮前后变化、分段读取、异常和完成状态。未请求 Telegram、未保存真实媒体，演示中的时间、字节数和百分比均不是性能测量。

## 3. 底层原理是什么

### 路径 A：恢复官方下载

WebK 查找媒体工具栏隐藏按钮，移除 `hide` 类。遇到匹配下载图标的按钮，记录点击回调，并让新播放器按钮调用官方下载。恢复的其他按钮不代表转发功能已经实测成功。（L740–805）

### 路径 B：自有媒体保存

1. 每 500 毫秒扫描目标页面结构。WebA 与 WebK 分别维护选择器和按钮注入逻辑。（L42、L485、L639）
2. 从 `img.src`、`video.src/currentSrc`、音频组件中取得当前媒体来源。部分视频地址末尾包含可解析的文件元数据。（L162–173）
3. 视频与音频使用 `fetch` 发出 `Range: bytes=offset-`，按响应 `Content-Range` 推进偏移量，检查起始位置和总大小。（L176–265、L329–408）
4. 支持 `showSaveFilePicker` 时创建可写文件，逐段写入；否则积累 Blob，组装对象 URL，并以 `<a download>` 触发保存。（L267–320、L410–465）
5. 图片走 `<a download>` 路径。（L468–480）

这里的 Range 是字节范围请求，分块大小由实际响应决定。示意网页采用固定等份块只是为了易懂，不代表上游固定分成五块。脚本没有自己实现 Telegram 登录、MTProto 协议或媒体解密；它复用网页端已有的取数环境。

### 实现取舍与缺口

| 发现 | 固定源码证据 | 可能影响与验证状态 |
| --- | --- | --- |
| 写入未返回到 Promise 等待链 | L238、L387；关闭后才记录完成，但视频 UI 在 L258 提前显示完成 | 失败未完整传递、成功状态时序有缺口；不能仅凭代码断定必然乱序或损坏，实际文件影响待复现 |
| 允许 HTTP 200，却仍强制解析 Content-Range | L186–203 | 缺失头部会解析失败，需分别验证 200 和 206 路径 |
| 音频 `finally` 中返回 Blob | L354–383 | JavaScript 的 finally 返回会覆盖异常或先前返回，完整性验证错误可能被吞掉 |
| 回退路径在内存中累积文件 | L151、L240、L271 | 大文件增加内存需求；未测内存峰值，也未确认统一的大小上限 |
| 进度框关闭只移除 DOM | L86–88；更新仍查询该 DOM | 没有真实取消机制；继续更新可能报错，不能宣传“支持取消” |
| 依赖具体 CSS 类名 | WebA Stories、媒体查看器等选择器 | 页面改版后可能失效；当前兼容性需账号测试 |

[Issue #164](https://github.com/Neet-Nestor/Telegram-Media-Downloader/issues/164) 讨论了多个完整性问题。本研究确认代码形态，未复现其全部后果，也未修改上游。

## 5. 可扩展方向是什么

优先处理“保存的文件能否可靠使用”，再增加批量和 AI：正确传递写入失败、等待关闭、区分 HTTP 响应、检查最终字节数、真实取消与重试；随后实现用户明确选择的队列、按来源命名、内容去重和索引。OCR、转写、摘要、全文搜索属于后续知识处理功能。

WebK/WebA 可拆成独立适配器，统一媒体描述与下载引擎。对有明确变化事件的页面，可评估 MutationObserver，减少持续轮询；这不保证减少所有兼容性维护。

完整优先顺序、前提和验收标准见 [扩展路线](reuse-roadmap.md)。上述扩展均未在本项目实现。

## 6. 对当前研究集的价值是什么

本研究集已有场景和游戏工程，这个项目补充的是“增强现有网页”的工具方向。最值得借鉴的是客户端能力复用、媒介差异处理和下载完整性，而不是增加一个下载图标本身。

如果 Telegram 是日常研究资料入口，后续“获授权采集 → 记录来源 → 整理 → 搜索”可能有直接效率价值；如果使用频率低，价值主要是技术学习。现阶段没有节省时间、下载速度、成功率、付费意愿或商业收益的实测数据。

## 8. 字节范围交互与扩展架构

网页使用 1,000 字节的假想文件、每段 200 字节说明范围计算。位置从 0 开始，结束位置也包含在范围内，长度为 `end - start + 1`。实际上游请求 `bytes=offset-`，块大小随响应而定。交互中的 206、200 和起点不匹配没有发送请求，也没有修复上游行为。

服务端可能忽略 Range 返回整个文件，200 与 206 应分别处理；后续段不能盲目追加全文件。读取 100% 也不能替代写入成功、关闭完成和完整性检查。协议依据：[MDN Range](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Range)，2026-10-11 核验。保存接口参考：[MDN showSaveFilePicker](https://developer.mozilla.org/en-US/docs/Web/API/Window/showSaveFilePicker)，浏览器行为尚未逐项实测。

扩展架构设想是“WebK / WebA 适配器 → 统一媒体描述 → 下载引擎 / 写入器 → 来源索引 / 搜索”。最小有用增量是文件加来源卡，再评估 OCR、转写和摘要；来源保留与外部传输范围应由用户控制。模块、队列、索引和模型流程尚未实现。
