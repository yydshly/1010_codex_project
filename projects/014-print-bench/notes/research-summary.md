## 能力：把可执行需求交付为可审查的模型改动

print-bench 的基础是参数化 OpenSCAD 设计、共享几何模块和工程脚本。尺寸、孔位、间隙、结构与部件关系由源码和参数表达；运行建模工具产生实际 STL 与多角度预览。源库中的 Nuggs Den 和 PIP piano hinge 发布图展示这类结构设计，不能据此推断任意角色、纹理、骨骼和动画都能自动生成。

对满足条件的 Issue，后台代理尝试理解要求、修改模型源码、补检查与说明并创建草稿 PR；人可以看到原需求、代码差异、生成图和验证结果。另有 design-run 流程处理 design-brief 新设计。它是带约束与工具的工程流程，不保证所有任务一次成功。

本次已经核验上游源码和公开 Issue / PR / Actions，并在本机复现一个孔洞朝向改动。这里发布的是完整研究网页和证据，不是在你的仓库安装自动修改模型的代理；原 X 视频真正作者和对应源码仍未确认。

## 模块：需求、策略、代理、几何、检查与交付分别负责什么

需求与队列层由 Issue、标签和任务约定组成；仓库内配置保存可复现策略，运行变量和凭据控制实际启停。Python 选择器执行确定的筛选规则，选择最旧、未领取且符合条件的一项任务。

调度层是 GitHub Actions Runner；模型登记表决定模型链与供应商；代理技能定义认领、验收冻结、分支、修改、预检和 PR。Claude Code Action 是运行框架，语言模型是另一层。已查配置从 Z.AI GLM 开始，配置三条 GLM 链路与 Anthropic 尾部，不能简单称为“全部由 Claude 模型完成”。

几何层是 designs 与 lib 的模型源码；生成层调用 OpenSCAD 和固定相机渲染；质量层使用几何与约束检查、网格检查和 PrusaSlicer 试切片；交付层使用 Git 提交和 PR。九个模块的具体文件、输入与职责见本页源码地图，所有链接固定在研究 commit。

## 原理：Issue 只是入口，Actions 执行工具，AI 修改源码

人写清目标、尺寸、限制和验收，为适合自主执行的任务加 autonomy-ok 标签。已查 backlog-burn 按每小时第 17 分钟计划运行，也可手动触发；计划任务可能排队延迟。Python 从队列挑一项，代理随后写 SHIP-LOCK 认领，并冻结验收范围。

代理读仓库规范，建立 claude/issue-N-slug 分支，修改 .scad、相关检查与说明，再调用工具执行。模型通过选择改法和调用工具改变代码；真正的几何由建模程序计算，检查结论来自实际执行。可编辑资产必须有源码、参数、依赖和可重复构建步骤。

预检和范围审计发现问题后，任务进入返修、停止或请求人判断；通过后创建关联 Issue 的草稿 PR。分支与版本保留差异和回滚点，维护者决定是否接受。完整流程不是在 GitHub 网页里运行 3D 编辑器，而是 Runner 检出仓库后执行程序。

GitHub 仓库存源码，Issue 存需求，Actions 调度与执行，PR 展示改动；GitHub Pages 只负责可选的静态展示。本研究页部署在 Pages，页面本身不承担远端建模或模型调用。双开关是配置 enabled 与运行变量 BACKLOG_BURN_ENABLED，复制源码不会自动继承启用状态与凭据。

## 真实效果与验证：Issue #398 → PR #424 → 几何确实改变

Issue #398 指出水滴孔尖顶误朝 −Z，应朝 +Z。PR #424 把共享 teardrop_hole 的 rotate([-90,0,0]) 改为 rotate([90,0,0])，同步铰链孔并更新说明、预览，2026-08-29 合并。定时 Actions #331 的公开注释明确关联 #398，记录任务成功且没有遗留锁。

本机 OpenSCAD 2021.01 编译同一最小测试件：12×14×12 mm 方块减去名义直径 6 mm、长度 16 mm 的孔，$fn=64。二进制 STL 的孔壁 Z 范围从 [−4.799988,+3.000000] 改为 [−3.000000,+4.799988] mm，确认扩展孔顶从下方翻到上方；两张正面图也是实际渲染。

这个实验验证一个具体源码改动的几何效果。图里的局部测试件不是整件产品前后对比；没有取得上游登录后的完整代理日志，没有在自有仓库运行 Issue→AI→PR 全链路，也没有实物打印。原始模块、STL、测量器、JSON、版本与授权都保留供回查。

## 价值：和直接对话能力相近，省的是重复组织与跟进

直接对话本来就能理解需求、修改源码、生成模型、测试并优化。自动化把这些操作固定为可排队、后台运行、可重复和可追踪的工作流；新价值主要来自工作组织与协作，而不是多了一种神奇的模型编辑能力。

它能减少每次启动环境、重复交代规范与上下文、催办下一步、手工整理截图和验证报告、建立分支和回查任务对应关系的工作。标准文件、依赖、输入、验收和交付留在仓库后，同类维护更容易批量处理和交接。

人仍需定义需求、建立验收、准备环境与凭据、处理失败、审查外观和范围。模型与 Runner 有费用、等待与错误，绿色 CI 也只覆盖已写下的规则；自动化不消除维护责任。

价值应按总耗时、合格率、返工、审查成本和费用评估，不能只看 PR 数。本研究没有测量你的实际节省工时、商业回报或批量成功率；这些收益是适用性分析。

## 使用场景：什么值得自动化，什么继续对话，什么只用脚本

适合目标明确、输出可验收、同类任务反复出现的工作：孔位与尺寸修复、配置兼容、素材约束、导出故障、字幕格式、说明与验证同步。开始时选小范围任务，保留失败样本和验收，让一次交付能被检查。

风格、剧情、造型探索与游戏手感通常要边看边改，目标会随效果变化，直接对话更自然。需求模糊、涉及大量跨模块改造时，先讨论并拆出可验证的部分；不要把一句模糊要求当成自动验收标准。

固定参数批量生成、定时测试和已有实验扫描，步骤确定时脚本或普通 Actions 就能完成。只有需要理解自然语言、选择修复方案、修改程序或解释实验差异时，才有必要引入模型。本页判断工具使用固定规则帮助选流程，不调用 AI。

## 可扩展方向：替换代理与建模工具，完善审查和任务管理

Codex 可替换“理解需求并改源码”的代理环节。官方 openai/codex-action@v1 安装 CLI，使用提供的 API 凭据并执行 codex exec。Issue 筛选、工具依赖、建模与检查、写入权限、分支和 PR 步骤仍由工作流组织；桌面登录不会自动成为 Actions 的 API 认证。本仓库尚未接入。

建模工具可扩展到 Blender Python、CadQuery、build123d、Three.js，从可打印零件到参数化场景、装配、材质或动画资产。更换工具时要相应准备源码接口、依赖和几何、拓扑、碰撞、材质、骨骼、动画或导出验收；不能只改模型名称便承诺任意 3D 效果。

审查层可增加固定相机前后对照、尺寸差异、装配与碰撞报告、打印风险说明和范围审计，让维护者更快判断结果。任务层可加模板、优先级、状态、预算、重试上限和失败转人工，并按真实合格率改进流程。

建议路线是：先规范现有项目输入与测试 → 选择一种高频小修复 → 跑通一条完整受控流程 → 对照省时与返工 → 再扩展工具和协作。用户目前理解原理但尚无接入必要，本网页用于形成可复用的研究资产，不擅自启动自动化。
